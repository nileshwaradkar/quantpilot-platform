# Render deployment

This is a concrete three-service deployment. It uses paid always-running compute; review Render's displayed charges before creating resources. No Render resources have been created by this code change.

## 1. Prepare accounts

- Create or sign in to your Render account and connect a private Git repository containing only `quantpilot-platform` contents at its root.
- For a platform used by other FYERS clients, arrange the appropriate FYERS third-party application and permissions. An individual application is not a substitute for a multi-user platform agreement.
- Arrange verified outbound IP configuration with FYERS before live execution. Render's ordinary outbound ranges are not a single dedicated address; its dedicated-IP offering is an additional paid capability. Verify how the allocated address set fits FYERS's registration limits.
- Configure an SMTP provider for verification and password recovery before public registration. A private invitation code supports the initial invited pilot.

Official references:
- https://render.com/docs/blueprint-spec
- https://render.com/docs/background-workers
- https://render.com/docs/outbound-ip-addresses
- https://render.com/docs/dedicated-ips
- https://fyers.in/api-docs/v3/getting-started/create-an-app/third-party-app/

## 2. Create the Blueprint

In Render choose **New → Blueprint**, select the repository, and use `render.yaml`.

Resources:
- `quantpilot-web`: Node web service, 0.5 CPU / 512 MB initial plan.
- `quantpilot-trading`: Node background worker, same initial size, exactly one instance.
- `quantpilot-db`: PostgreSQL 17, private network only, initial small paid plan.

These are starting capacities for a controlled pilot, not validated capacity guarantees.

The build runs TypeScript compilation and tests on the web service. Both services run the migration command before starting. Migration application is serialized using a PostgreSQL advisory transaction lock. The worker uses a separate lifetime lease to prevent duplicate executors.

## 3. Configure environment values

- `APP_ORIGIN`: exact public HTTPS origin, such as your assigned `https://your-service.onrender.com` URL, without a trailing path. If Render assigns a different hostname, correct it before sign-in.
- `ENCRYPTION_KEY`: generated by the Blueprint and shared with the worker. Back it up securely. Changing it without migrating stored tokens prevents decryption.
- `REGISTRATION_CODE`: generated private-pilot invitation code. Share only with invited users. Invited accounts are trusted as verified. For public registration, configure SMTP, then remove this code so email verification becomes mandatory.
- `FYERS_APP_ID`, `FYERS_APP_SECRET`: shared platform app credentials. Users authorize their own broker accounts through OAuth; they do not supply the platform secret.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`: email delivery settings. Optional for an invited pilot; necessary for public signup/password recovery.
- `NSE_HOLIDAYS`, `MCX_HOLIDAYS`: comma-separated YYYY-MM-DD dates. Apply identical schedule settings to the web service and worker.
- `MCX_SQUARE_OFF`: default 23:00 IST; confirm the broker's applicable session cutoff.

The worker references the web service's shared credentials and live flags. After changing shared values, sync/redeploy both services; referenced values are not assumed to update every running process automatically.

Keep these false until all broker acceptance checks pass:
```text
LIVE_TRADING_ENABLED=false
BROKER_APP_APPROVED=false
DEDICATED_EGRESS_CONFIRMED=false
```

The flags describe required operator verification. Merely setting them does not perform or prove those checks.

## 4. Configure FYERS redirect

Set the authorized redirect URI to:

```text
https://YOUR-HOST/api/broker/callback
```

It must match APP_ORIGIN exactly, including scheme and hostname.

## 5. Validate deployment

1. Confirm the web service's `/healthz` responds successfully.
2. Confirm the worker is running and dashboard shows its current heartbeat.
3. Register an invited account, or verify email through SMTP.
4. Connect FYERS using the account owner's normal broker authorization flow.
5. Choose Paper → Options → configure a market's risk.
6. Start monitoring explicitly. Confirm daily levels, ATM contract, expiry, multiplier and timestamps against FYERS.
7. Run the paper/recovery test matrix in ACCEPTANCE.md.
8. Enable and test backups, restore, alerts and log access before a live pilot.

## Deployment and rollback

Automatic deployment is off. Deploy outside exchange sessions with entry monitoring paused and positions flat where possible. Existing order intents and positions are persisted; after any worker restart, new entries remain paused until explicitly restarted, while existing trades are reconciled.

One worker may wait in standby while the previous deployment owns the lease. A missing/expired heartbeat blocks new starts. Keep the native PostgreSQL connection URL for the worker lease; transaction-pooling URLs cannot hold a session advisory lock reliably.

Roll back application code only to a schema-compatible version. Do not drop tables to recover a failed deploy. Take a backup before schema changes.

## What is still external work

This workspace has no connected Render deployment/account or production FYERS credentials. The Blueprint is prepared, not remotely deployed. Render billing/account setup, broker approval, dedicated egress verification, SMTP delivery and live acceptance testing require the owner's accounts. The local preview is not a remotely hosted URL.
